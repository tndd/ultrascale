# 画質調査 — 2026-10-15

目的は文字・細線を含む画面の見やすさを改善すること。画素差やAPIの成功を最終成果と扱わない。

## 最新状態（ロック解除後）

- 修正版0.2.0を再インストール。通常HiDPIへの復旧中に監視タイマーが表示を解除する競合を修正。修正前相当で失敗、修正後に成功する回帰テストを確認した。
- 通常125%の17秒以上の維持を確認。その後ユーザーが表示を良好と報告した時点の実測は通常120%、論理2867×1200、描画5734×2400、物理3440×1440。追加フィルタを使わない通常ミラーで、色ID81・タイミング44だった。ただし、小さい文字には甘さが残るとの指摘あり。
- 出力変更APIで色81→74を10秒維持し81へ復元。さらに120%のまま20秒間比較し、ユーザーの評価は「変わらない」。各秒の読出しと復元後の読出しが一致した。この比較では色形式変更による文字の改善は確認できなかった。
- EDIDのNativeFormatは1920×1080を報告するが、実際のドライバタイミングは3440×1440。NativeFormatだけで対象を識別すると見落とすため、読み取り専用診断に実タイミングと候補色形式を追加した。
- アプリの画面収録・アクセシビリティ判定は依然false。設定画面には登録があり、オン・オフの反復でも解決しなかった。ユーザーの設定漏れとは断定しない。
- 外部画面の取得画像にはCodexの本文が含まれず、画質評価に使えなかった。組み込みブラウザで本文を表示したが、これは出力後の画質の証拠ではない。通常のPlaywrightで取得するページ画像も物理出力段階を含まず、この確認を代替できない。
- 通常120%を維持し、追加フィルタは実機検証が未完了のまま公開しない。以下の差し戻し・未実行の記述は、この追加検証より前の経過である。

## 初回調査で確認できたこと

- macOS 15.8.1、Apple Silicon、Mi 3440×1440。通常125%は論理2752×1152、描画5504×2304から縮小する。調査冒頭に通常125%を再適用できた。
- 試験版の画質調整は権限チェックで失敗。実画面が鮮明になったという証拠はまだない。画面収録とアクセシビリティの不足を分けて表示する修正を追加した。
- 途中でMacがロック状態になった。WindowServerにはUltraScaleのウインドウがあったが、操作先はloginwindowの「ログイン」画面だった。AXウインドウ数0をアプリの起動失敗と混同しない。
- `/Applications/UltraScale.app` は配布済み0.1.3へ差し戻した。元のZIPとのSHA-256一致を確認：`0121d5a30924a8d1166efb3ec200ffcbb0adcdbfc455165eff18b2f8fd6ad577`。
- 差し戻し後の125%再適用はロック解除待ち。最後の状態は通常3440×1440、仮想画面なし。復旧完了とは扱わない。

## 下位レイヤーの調査

このMacのIOMobileFramebuffer接続ライブラリを`dyld_info -exports`と`-disassemble`で調べた。カーネルドライバー全体やDCPファームウェアの解析完了を意味しない。対象UUIDは `41CED59B-B76F-31FB-8785-3E39CA6AAE9E`。

- IOMobileFramebufferShimへ`IOMobileFramebufferOpen`で接続し、`IOMobileFramebufferGetDigitalOutMode`を実行。両戻り値0で、色ID81・タイミングID44を取得できた。
- APIの出力引数順は色ID、タイミングID。初回は逆と仮定していたため、IORegistryのIDと照合して修正した。
- 色81の登録値：Depth=10、PixelEncoding=3、DynamicRange=1、Colorimetry=1。タイミング44：Active=3440×1440、約60Hz、IsOverscanned=false。
- 色74はDepth=8、PixelEncoding=0、DynamicRange=0、Colorimetry=10で、次の比較候補。同名enumが別APIにあっても数値の意味を流用して断定しない。
- GetDigitalOutModeは内部関数へ0x40と44バイトの応答領域を渡し、成功時に2整数を返す。SetDigitalOutModeは別の関数ポインターへ転送する。変更APIは未実行。
- SkyLightに出力モード変更とウインドウ用Core Imageフィルタのシンボルがある。存在だけで全画面の縮小や文字描画へ適用可能とは判断できない。
- IOAVServiceCopyDiagnosticsStringはこのOSでは即座にNULLを返す実装。診断文字列による確認はできなかった。

## 画像処理の比較

日本語・英数字・色付き文字・細線を2倍描画し、125%相当の物理寸法へ縮小する。直接同じ物理寸法で描画した参考、3種類の縮小、Lanczos＋強度25/75を比較した。

```sh
xcrun clang -fobjc-arc -Wall -Wextra -Werror -framework Cocoa -framework CoreImage -I Sources Sources/ImagePipeline.m scripts/quality-comparison.m -o build/quality-comparison
./build/quality-comparison build/quality-comparison.png
```

強度75では文字と細線が濃くなる一方、輪郭の縁取りが増える。元の形や情報が復元されたという意味ではない。等倍で比較する。これは処理関数の出力比較であり、実機ストリームの提示やパネル上の最終画質の検証にはならない。

## 判断と一次資料

## 2026-10-15 外部モニタを使わない検証基盤

目的は「呼び出しに成功した」「画素が変わった」「読みやすくなった」を区別すること。今回の試験は画面設定を変更せず、実行中のUltraScaleも再起動しない。

| 段階 | 外部モニタなしで確認できること | 今回の結果 |
| --- | --- | --- |
| 画像処理 | 本番と同じ関数の出力、縮小・シャープネスの差、輪郭の広がり・縁取り | 100/120/125/150/200%の画素検証成功 |
| 非公開API | シンボル、生成結果、入力キー、明示的エラー | 下記のプローブで採取 |
| WindowServer・提示 | 仮想画面、合成後の画素、GPU提示、復元 | 既存の`./test.sh --virtual`は通常モードの制御用。今回未実行。新規合成フィルタの画素効果は未検証 |
| 物理出力 | ケーブルの色形式、パネルの配列、実際の小さい文字 | オフスクリーン試験では確認できない |

`./verify-quality.sh`は全文字素材と灰色境界を生成し、アプリと同じ`Sources/ImagePipeline.m`をMetal上で実行する。レポートはOS/GPU、寸法、入力画像・処理ソース・出力画素のSHA-256を保存する。縮小対象は現行の3440×1440比較に固定しており、このテストだけで他の解像度の品質は保証しない。

32→224の灰色境界を4位置で測り、10〜90%遷移幅の平均、元の範囲からはみ出る縁取りの最大、灰色のRGB差を記録する。これは画像内の値であり、パネルの輝度応答、MTF、文字認識率ではない。強調で遷移幅が狭くなっても、縁取りが増えれば改善とは限らない。

測定系自体にも故意のGaussianぼけ、黒い縁取り、同一画像を入力して検出を確認する。`--inject-noop`で本番関数へ渡すシャープネスを0に固定すると、効果判定が失敗して終了コード1になる。200%は入力と出力が同寸法なので、縮小方式による差を要求せず1:1を確認する。

### 非公開の合成API：生成と効果を分離

```sh
mkdir -p build
xcrun clang -fobjc-arc -Wall -Wextra -Werror -framework Cocoa scripts/probe-compositor.m -o build/probe-compositor
./build/probe-compositor > build/compositor-capabilities.json
```

このプローブは非表示の自ウインドウでWindowServer接続を作り、自プロセスのフィルタ生成・設定・解放を試す。画面には適用せず、権限要求もしない。終了コード0は診断の採取成功であり、フィルタ対応の意味ではない。

- macOS 15.8.1のSkyLightでは`SLSNewCIFilterByName`等のシンボルは存在する。しかし有効な接続と自ウインドウがある状態でも、`CIColorControls`、`CISharpenLuminance`、`CIUnsharpMask`はすべて生成結果1006、ハンドルなし。存在しない名前の対照も同じ結果だった。この経路での適用成功は確認できない。原因が権限か互換性かも、この戻り値だけでは断定できない。
- `SLSSetWindowFiltering`はこのOSの逆アセンブルでは即座に戻る。名前だけで縮小フィルタ変更に使えると判断してはいけない。
- 別経路のCore Animation `CAFilter`では37種類が列挙された。`lanczosResize`、`luminanceCurveMap`、`colorMatrix`、`gaussianBlur`のオブジェクト生成と入力キー取得に成功した。例えば`lanczosResize`は`inputScale`、`inputAspectRatio`を持つ。ただしレイヤー・背景・全デスクトップに効くことはまだ証明していない。
- BetterDisplayの公開ガイドには、画面収録経路とは別の合成フィルタ経路が記載されている。従ってmacOSで合成段階の調整が全面的に不可能とはいえない。一方、同製品が使う内部実装を今回特定したわけではない。

次の実験は、自作の文字ウインドウ／レイヤーにCore Animationフィルタを適用し、無効時・有効時・故意の強いぼけを比較すること。まず既知の画素が変わる証拠を得てから背景合成へ進む。`renderInContext:`等のCPU描画がWindowServerの合成経路を再現するとは仮定せず、取得した画素がどの段階のものかを記録する。

### 低レイヤーでできる範囲と限界

有望なのは、適切な解像度での描画、余分な再縮小の削減、縮小カーネルや局所コントラストの選択である。これは小さい文字の輪郭に影響しうる。色形式変更は今回の比較では改善が見られず、優先度を下げる。

完成したRGB画像から各アプリの文字輪郭・ヒンティングを完全には取り戻せない。WindowsのDirectWrite/ClearTypeは文字描画段階の処理なので、画面全体の後処理と同等ではない。サブピクセルの配列を利用する処理には実パネルの配列・方向・最終1:1対応が必要で、外部モニタなしの合格をそのまま流用できない。

DCPはフレームバッファーの合成・スケーリングに関わるため調査対象になるが、ドライバやファームウェアの制御口が見つかっただけでは、任意の高品質フィルタや全アプリの文字描画置換ができるとはいえない。今回確認したのはユーザー空間ライブラリの入口とオブジェクト生成までであり、カーネル/DCP改変による画質改善の成果はない。
